# 项目架构文档

> 版本: v0.17 (2026-10-02, world/ 建筑内 interior 标志 + 垂直缩放 vertical_scale; 新增 visibility/ 渲染遮挡模块: 规则 A 高层溶解 + 规则 B 墙裁剪; world_scene 接入 3m 墙高与数据驱动遮挡)
>
> 本文档记录项目的整体架构、技术选型、模块设计与关键架构决策。
> 依据 `AGENTS.md` 约定: 当依赖库、项目架构或其他相关内容发生变化时, 必须同步更新本文档。

## 1. 项目概述

- 项目名称: project_phoenix
- 项目定位: 基于 [raylib](https://www.raylib.com/) 的 C++17 桌面程序, 集成 spdlog 日志与 LuaJIT + sol2 脚本绑定
- 当前阶段: 技术验证阶段。`core/main.cpp` 目前是验证「窗口 + 渲染 + ImGui + 模型加载 + 日志 + LuaJIT + sol2 脚本绑定」集成的示例程序, 尚无业务功能

## 3. 总体架构

当前为**单体可执行文件**结构, 由 `core` 单一目标构成。逻辑上分两层:

```text
┌─────────────────────────────────────┐
│  应用层: app/ (App + Game)           │  窗口 / 主循环 / 固定 tick + 业务载体
│  └── main.cpp (入口, 组装 App)       │
├─────────────────────────────────────┤
│  基础设施层                          │
│  ├── log/    (spdlog 封装)           │  第三方库不直接暴露给应用层
│  ├── script/ (LuaJIT 持久引擎, sol2)  │
│  ├── event/  (事件总线)              │
│  ├── config/ (JSON 配置, nlohmann/json)│
│  ├── ecs/    (ECS 骨架, entt)        │
│  ├── camera/ (相机系统骨架)           │
│  ├── input/  (输入抽象)               │
│  ├── world/  (世界与地图, chunk tile)  │
│  ├── model/  (raylib 模型封装)       │
│  └── util/   (asset_path 等工具)     │
└─────────────────────────────────────┘
```

核心设计原则:

- **第三方库隔离封装**: 每个第三方库通过独立模块封装后再被应用层使用, 避免第三方头文件互相冲突(见 §6)。
- **依赖版本全固定**: 源码依赖通过 `URL + SHA256` 固定, vcpkg 依赖通过 `builtin-baseline` 固定, 保证构建可复现。
- **Windows 仅支持 MSVC**: 受 vcpkg triplet 与 ABI 约束(见 §7)。

## 5. 构建系统

### 5.1 CMake 层次

- **顶层 `CMakeLists.txt`**: 只负责依赖获取与全局约束, 不直接编译业务代码
  - `find_package(spdlog / sol2 / Catch2 / nlohmann_json / EnTT)` 从 vcpkg 获取; LuaJIT 经 `find_path / find_library` 定位 (luajit port 仅导出 pkgconfig, 无 CMake config)
  - `enable_testing()` 启用 ctest 调度
  - `FetchContent` 获取 raylib 6.0、Dear ImGui 1.92.7、rlImGui 源码
  - ImGui 与 rlImGui 均不提供官方 CMake 配置, 由顶层手动编入静态库 `rlimgui`
  - 强制关闭 raylib 的 `BUILD_EXAMPLES` / `BUILD_SHARED_LIBS` / `USE_EXTERNAL_GLFW`
- **`core/CMakeLists.txt`**: 定义可执行目标 `project_phoenix`, 链接 `raylib rlimgui spdlog::spdlog ${LUAJIT_LIBRARY} sol2::sol2 nlohmann_json::nlohmann_json EnTT::EnTT`; 另定义测试目标 `project_phoenix_tests` (复用 `log/` 与 `script/` 源文件, 链接 `Catch2::Catch2WithMain`, 不链接 raylib/model_loader), 经 `add_test` 接入 ctest

### 5.2 vcpkg (manifest 模式)

- 依赖清单与版本基线集中在 `vcpkg.json` (`builtin-baseline` 固定)
- preset 通过 `VCPKG_ROOT` 环境变量接入 vcpkg toolchain
- Windows triplet: `x64-windows-static-md` (静态库 + 动态 CRT)

### 5.3 构建 Preset

| Preset | 平台 | 说明 |
|---|---|---|
| `msvc-debug` / `msvc-release` | Windows | Ninja + cl (MSVC) |
| `linux-debug` / `linux-release` | Linux | Ninja + GCC/Clang |

同名 `testPresets` 与 configure/build preset 一一对应, 供 `ctest --preset <name>` 直接运行单元测试。

## 6. 模块设计

### 6.1 `log/` — 日志封装

- `namespace app_log`, 对 spdlog 做薄封装: `init()` / `debug()` / `info()` / `warn()` / `error()` / `critical()`
- `init()` 统一设置日志 pattern (`[%H:%M:%S.%e] [%^%l%$] %v`) 与级别 (debug)
- **设计动机**: spdlog 在 Windows 上会引入 `<windows.h>`, 与 `raylib.h` 在同一源文件中存在宏冲突; 独立成模块后, 应用层只 include `app_log.h`, 隔离冲突

### 6.2 `script/` — LuaJIT 持久脚本引擎 (sol2 封装)

- `namespace lua_engine`, 类 `Engine` — 基于 sol2 的持久脚本引擎:
  - 构造时创建 `sol::state` 并 `open_libraries()` (无参, 确保 `jit` 注册为全局变量)
  - `bool do_file(const std::string& path)`: 加载并执行一个 `.lua` 文件; 出错经 `app_log::error` 输出并返回 `false`
  - `bool reload(const std::string& path)`: 重新执行已加载文件 (手动基础重载, 覆盖全局量; 函数级/自动监听热重载留到 P7)
  - `Value call_function(const std::string& name)`: 调用全局函数并返回基础类型值 (nil / bool / number / string); P0 仅无参, 参数与对象绑定在 P0-04 扩展
- `class Value` — 基础类型值包装 (`std::variant<monostate, bool, double, string>`), 隔离 sol2 类型, 应用层不直接接触 `sol::object` (ADR-5)
- `sol::state` 以 pimpl 形式持有在 `lua_engine.cpp`, sol2 头文件不向应用层暴露 (ADR-5)
- 路径解析: `do_file` 接收显式路径, 运行时复用 `asset_path::resolve` 定位 `lua/` 脚本; 单元测试经 CMake compile definition `PROJECT_PHOENIX_LUA_DIR` 注入 `lua/` 绝对路径 (无头可跑)
- `namespace api` — API 绑定框架 (`api_registry`): 建立 `api.<module>.<func>` 注册约定, 每个业务模块提供 `register_<module>(lua_State*)`, 由 `register_all(Engine&)` 统一汇总挂到 `api` 表。`Engine::raw_state()` 暴露内部 `sol::state` 的裸 `lua_State*` 供绑定层使用, sol2 头仅出现在 `api_registry.cpp` (ADR-5)。P0-04 绑定 `api.log.*` (→ `app_log`) 与 `api.util.add` (返回值链路演示); P0-05 新增 `register_event(lua_State*, event::Bus&)` 绑定 `api.event.*` (事件总线, 需注入 `event::Bus` 实例); P0-08 新增 `register_camera(lua_State*, camera::Manager&)` 绑定 `api.camera.*` (相机, 需注入 `camera::Manager` 实例); P1-01 新增 `register_input(lua_State*, input::Manager&)` 绑定 `api.input.*` (输入绑定, 需注入 `input::Manager` 实例)

### 6.3 `model/` — 模型加载与动画封装

- `namespace model_loader`, 类 `ModelScene`, 对 raylib 模型 API 做薄封装:
  - `load(path, &error)`: `LoadModel` + `LoadModelAnimations`(glTF/GLB 等), 失败判定 `meshCount == 0`; 内部缓存模型与动画数组
  - `update(dt)`: 动画推进 (60fps 基准, `UpdateModelAnimation`), 支持选择 / 播放暂停 / 循环 / 速度
  - `draw(transform, drawWires)` / `drawBounds(transform)`: `DrawModelEx` / `DrawModelWiresEx` / `GetModelBoundingBox` + `DrawBoundingBox`
  - `bounds()` / `stats()`: 包围盒与网格统计, 供相机适配与 UI 展示
  - `applyTexture(mapType, path)`: 动态加载贴图并绑定到模型所有材质的指定贴图槽 (`MaterialMapType` 枚举对应 raylib `MaterialMapIndex`, 支持基础色 / 法线 / 遮罩等), 供应用层运行时换贴图
- **设计动机**: 与 `log/`、`script/` 一致, raylib 类型不向应用层暴露 (ADR-5); 应用层通过纯数据 struct `Transform` 控制模型变换

### 6.4 `app/` — 应用框架层

`main.cpp` 瘦身为纯入口: `app_log::init()` → 组装 `SceneHost`(注册各场景) → 创建 `app::App(std::make_unique<SceneHost>())` → `app.run()`。

- `app::Game` — 业务载体抽象接口: `init()` / `update(fixedDt)` / `render(alpha)` / `renderUi()` / `shutdown()`, 供后续真实游戏场景替换 (ADR-10)。`render` 绘制 3D 内容, `renderUi` 绘制本场景 ImGui 面板, 帧所有权 (`Begin/EndDrawing` + `rlImGuiBegin/End`) 由 `SceneHost` 持有。
- `app::App` — 应用外壳: 负责 `InitWindow` / `SetTargetFPS(60)` / CJK 字体 / `rlImGuiSetup` / 主循环 / `rlImGuiShutdown` / `CloseWindow` 等框架级职责, 不依赖具体业务。
- `app::SceneHost` — 场景切换载体 (实现 `Game`): 持有多个命名场景并委托给活动场景, 支持「大类/场景名」两级命名与懒初始化, 可在任意场景间自由切换; 渲染帧内绘制统一顶部场景选择器 (P0-09 引入)。

场景按「大类」分目录组织在 `scene/` 下, 用 `scene::` 子命名空间, 每类可含多个场景:

- `scene/menu/` — 游戏菜单 (预留, `scene::menu`)。
- `scene/debug/` — 调试: `scene::debug::ModelViewerGame` (原 `app/` 下的模型查看器, 迁移至此)。
- `scene/main_game/` — 主游戏: `scene::main_game::DemoScene` (P0-09 端到端集成 demo 场景)。

初始化顺序: `app_log::init()`(main) → `InitWindow`(默认 2560×1440, 2K) → CJK 字体 → `game.init()`(默认 demo 场景) → 主循环 → `game.shutdown()` → `rlImGuiShutdown` / `CloseWindow`。

模型查看器主循环内 (迁移至 `scene/debug/model_viewer_game.cpp`):
- ImGui 面板分「模型」「相机」折叠组: 模型路径加载、变换参数、动画控制; 相机位置 / 目标 / up / FOV / 投影 / 预设视角 / 适配模型 / 鼠标环绕控制 / 手动飞行控制
- 相机控制支持两种互斥模式:
  - **环绕控制**: `UpdateCamera(CAMERA_ORBITAL)`, 鼠标绕目标点旋转 + 滚轮缩放
  - **手动飞行**: 匿名命名空间辅助函数 `updateManualCamera`, 编辑器风格 `W/A/S/D` 前后左右(以视角朝向为准, 含垂直分量) + `空格/Ctrl` 升降 + 按住右键捕获鼠标旋转视角; 复用 raylib `rcamera.h` 的 `CameraMoveForward/MoveRight/MoveUp/Yaw/Pitch` 原语(`model_viewer_game.cpp` 需额外 `#include "rcamera.h"`, 因 `raylib.h` 仅暴露 `UpdateCamera/UpdateCameraPro`); 移动速度 / 旋转速度可在 ImGui 中配置, 右键旋转时经 `DisableCursor` 捕获鼠标, 期间置位 `ImGuiConfigFlags_NoMouseCursorChange` 以避免与 rlImGui 的每帧光标管理冲突

### 6.5 `app/` — 固定 tick 主循环

采用「Fix Your Timestep」累加器模式: `FIXED_DT = 1/30`, 帧时间累加到 `accumulator` 后, 每次扣减 `FIXED_DT` 调用一次 `game_->update(FIXED_DT)` (可能一次或多次追帧); `render(alpha)` 每帧调用一次, `alpha = accumulator / FIXED_DT` (∈ [0,1)) 供渲染插值。帧时间上限 `0.25s` 防止卡顿后累加器死亡螺旋。每秒经 `app_log` 输出一次 tick 计数, 用于人工核对逻辑以 30Hz 推进。

### 6.6 `util/` — 通用工具

- `namespace asset_path` — `resolve(requested)`: 依次尝试原始路径、逐级 `../` 前缀(最多 4 层)、可执行文件目录, 兼容不同工作目录 (如 IDE 将工作目录设为 `build/` 子目录); 未找到返回原始路径交由加载器报错。抽自原 `main.cpp` 的 `resolveAssetPath`, 供后续 `config/` 等复用。

### 6.7 `event/` — 事件总线

- `namespace event` — 纯 C++ 事件总线, 不依赖 sol2 / Lua, 供 C++ 与 Lua 双端订阅与分发:
  - `class Value` — 载荷值, `std::variant<monostate, bool, double, string>` 收敛四类基础类型 (nil / bool / number / string), 语义对齐 `lua_engine::Value`; 提供 `nil()` / `boolean()` / `number()` / `string()` 静态工厂。
  - `class Bus` — 事件名 → 订阅列表的订阅表, 同步分发: `on(name, handler)` 返回订阅 id、`off(name, id)` 精确移除、`emit(name, payload)` 遍历订阅逐个调用 (快照遍历避免回调中增删订阅导致迭代器失效)。
- Lua 绑定在 `script/api_registry` 的 `register_event(lua_State*, event::Bus&)` 中: `api.event.on(name, func)` (同名多 handler) / `api.event.off(name)` (按名移除全部) / `api.event.emit(name, payload?)`; Lua handler 以 `shared_ptr<sol::protected_function>` 保存防 GC, 载荷经绑定层 `event::Value ↔ sol::object` 互转 (ADR-5)。
- **设计动机**: 与 `log/`、`script/` 一致, `event/` 是底层基础设施, 不反向依赖脚本层; 事件是 C++ 与 Lua 双向解耦通信的中介, 为 P0-09 端到端链路 (触发事件 → Lua 处理) 打基础。

### 6.8 `config/` — 配置系统

- `namespace config` — 纯逻辑 JSON 配置层, 只依赖标准库 + nlohmann/json, **不依赖 raylib / asset_path / sol2 / lua_engine** (可无头单元测试):
  - `class Document` — 配置文档, 包装一份已解析的 JSON 对象, 提供类型安全读取与校验; 采用 pimpl 隔离 nlohmann/json 头文件 (ADR-5), 公开头不暴露第三方类型。
  - 读取接口: `get_bool` / `get_int` / `get_double` / `get_string(path, def)`, 按点分隔路径 (如 `"window.title"`) 嵌套访问; 字段不存在或类型不匹配时返回默认值。
  - 子键枚举: `keys(path)` 返回指定路径下对象/数组的子键名列表 (对象返回键名, 数组返回索引字符串 `"0".."N-1"`, 节点不存在或非容器返回空), 供遍历嵌套对象/数组 (如输入绑定表、地图 JSON)。
  - 容器长度: `size(path)` 返回对象/数组元素个数 (节点不存在或非容器返回 -1)。
  - 点分隔路径支持**数字下标段**: 全数字段对数组按索引取值 (如 `"levels.0.tiles.42"`、`"tile_defs.0.color.1"`), 与对象 key 匹配共存 (对象优先按 key 匹配)。
  - 校验接口: `validate(required, optional)` 仅校验顶层字段, 返回缺失必填字段 (`missing`) 与未声明未知字段 (`unknown`)。
  - `load_file(path)` — 从文件加载 JSON 文档, 文件不存在或解析失败返回 `std::nullopt` (经 `app_log::error` 输出); 用 nlohmann 非异常 `parse(..., false)` + `is_discarded()` 判断失败, 避免依赖 `/EHsc`。
- **路径解析职责分离**: `load_file` 接受已可用的文件系统路径, 不做工作目录回退; 运行时路径解析由调用方 (app 层) 用 `asset_path::resolve` 完成 (P0-09 集成时落地), 单元测试用 `PROJECT_PHOENIX_CONFIG_DIR` 注入的绝对路径加载。
- **设计动机**: 与 `log/`、`event/` 一致, `config/` 是底层基础设施, 不反向依赖脚本层; 为 P0 总验收「C++ 读配置并驱动初始化」提供 JSON 数据源, 由 C++ 核心在 P0-09 端到端链路中加载并解析 (不新增 `api.config`, 配置不经 Lua)。

### 6.9 `ecs/` — ECS 骨架

- `namespace ecs` — 纯 C++ ECS 骨架, 只依赖标准库 + entt, **不依赖 raylib / sol2 / lua_engine / config / event** (可无头单元测试):
  - `using Entity = entt::entity` — 直接采用 entt 原生实体句柄 (uint32), 为后续 Lua 侧 number 互转保留语义; `ecs::null` 为空实体哨兵。
  - `class Registry` — `entt::registry` 的 header-only 薄封装: `create` / `destroy` / `alive`(实体生命周期)、`attach` / `attach_or_replace` / `detach` / `has` / `get`(组件)、`view<Component...>()`(按组件组合查询, range-for 直接迭代 `Entity`)。
  - `using System = std::function<void(Registry&, float)>` — 约定统一 system 签名。
  - `class SystemManager` — system 注册 + 统一更新循环: `add(System)` 按注册顺序追加、`update(Registry&, float)` 按序调用每个 system。
- **预留 Lua 规则接口（程度一：仅定形、不接 Lua）**: `System` 即稳定的规则扩展点, 未来「Lua 规则」= 一个内部派发到 `lua_engine::Engine` 的 `System`(由 `script/` 侧适配器构造), 无需改动 `ecs/` 即可接入; 依赖方向为 `script/ → ecs/`, 本阶段 `ecs/` 不引入 Lua 依赖。
- **ADR-5 特例（header-only 薄封装）**: entt 是 header-only 且重度模板化, `attach<T>` / `get<T>` / `view<T...>` 必须在知道 `T` 完整定义处实例化, 无法用 pimpl 完全隔离; 故 `ecs.h` 作为全项目**唯一** include `<entt/entt.hpp>` 的地方, 应用层只 include `ecs/ecs.h`、只接触 `ecs::` 类型, 精神上延续「应用层不直接依赖第三方头」。
- **设计动机**: `ecs/` 是承载实体/组件/系统的底层基础设施, 为 P0-09 端到端链路「ECS 创建玩家实体」及后续游戏逻辑打底。
- **`ecs/components.h` 正式组件**（P1-03 引入）: `struct Position { float x,y,z; }` + `struct Mover { float speed; std::int32_t level; }`, header-only 纯数据, 供 `movement/`（移动碰撞）、`scene/main_game/world_scene`（玩家实体）、后续 P1-04 相机跟随 / P1-05 `api.ecs` 复用, 避免这些模块反向依赖 `movement/`。

### 6.10 `camera/` — 相机系统骨架

- `namespace camera` — 相机系统骨架, 纯逻辑核心 + 独立 raylib 适配层:
  - `using Id = std::uint32_t` — 相机实例 id (`kInvalidId = 0`), 与名称 (string) 双标识。
  - `enum class Type { Isometric }` — 相机类型 (P0 仅 isometric 验证载体)。
  - `struct Params` — 相机参数 (pos/target/up 三分量数组 + fovy + projection + distance), 语义对齐 raylib `Camera3D`, 不依赖 raylib。
  - `apply_isometric(Params&)` — isometric 位置推导 `position = target + normalize(1,1,1) * distance` (纯函数, 可单测)。
  - `class Manager` — 多相机实例管理: `create`(名称冲突返回 kInvalidId) / `destroy` / `has` / `find` / `names`(list) / `set_active`(按名称或 id) / `active` / `active_name` / `params` / `active_params` / `set_param`(按 key 改参数, 支持 fov/fovy、distance、pos_x/y/z、target_x/y/z、up_x/y/z、projection)。
  - isometric 相机在 `create` / `set_param` 后自动 `apply_isometric` 重算位置 (改 distance/target 联动位置)。
- raylib 适配层 `camera/camera_raylib.h` (header-only): `to_camera3d(const Params&)` 字段直拷为 raylib `Camera3D`; 仅运行侧 include (测试目标不链接 raylib)。
- Lua 绑定 `script/api_registry` 的 `register_camera(lua_State*, camera::Manager&)`: `api.camera.get_active` / `get_active_id` / `switch`(名称或 id) / `set_param`(key, value) / `list`(名称表); `shake` / `set_follow` 占位返回 false。
- **设计动机**: 与 `log/`、`event/` 一致, `camera/` 纯逻辑核心不依赖 raylib/sol2 (可无头测试), raylib 适配层隔离第三方类型; 为 P0-09 端到端链路「调 api.camera.switch」打底。

### 6.11 `input/` — 输入抽象

- `namespace input` — 输入抽象层, 纯逻辑核心 + 独立 raylib 适配层 (对齐 ADR-5 / ADR-9):
  - `enum class Key` — 按键标识 (字母/数字/方向/功能/修饰键), 与 raylib `KeyboardKey` 解耦; 与字符串名称双向转换 `key_from_name` / `key_name` (名称规范: 单字母大写 `"W"`、数字 `"0".."9"`、特殊键全大写 `"SPACE"` / `"LEFT_SHIFT"`)。
  - `enum class ActionState { Idle, Pressed, Held, Released }` — 动作状态 (每固定 tick 采样一次)。
  - `struct Vec2 { x, z }` + `action_to_dir(action)` — 动作 → 水平面单位向量 (P1 仅 `move_up/down/left/right`, 对齐 roadmap §1.1)。
  - `class BindingMap` — 动作 ↔ 按键绑定表, 含**静态冲突检测**: `bind(action, key, force?)` 时若该键已被同表其他动作占用, 默认返回 `Conflict` 并保留原绑定 (经 `app_log::warn`), `force=true` 强制顶替; 反向查询 `actions_for(key)`。
  - `class Manager` — 命名上下文管理 + 采样状态机: `context(name)` 幂等创建、`set_context(name)` 切换活动上下文 (场景级隔离)、`sample(pressed_keys)` 按「上一/本 tick 按下」输出边沿与持续状态、`state(action)` / `query(action)` 查询。
  - `load_bindings(Manager&, const config::Document&)` — 从配置文档读 `default_context` 与 `contexts.*` 并绑定 (依赖 `config` 纯头, 未知键名跳过告警)。
- **按键冲突检测分两层**: ① 静态 — 同上下文内同键多动作, `bind` 时检测并默认拒绝; ② 动态路由 — 不同场景/窗口通过「命名上下文 + 优先级栈」隔离, 同一键在不同上下文绑定不同动作是设计目标而非冲突, 采样时按上下文优先级路由。P1 落地「场景级 `set_context` 切换」,「窗口优先级栈」预留接口 (UI 需求再实装)。
- raylib 适配层 `input/input_raylib.h` (header-only): `to_raylib_key(Key)` 键值映射 + `sample_pressed_keys()` 读取当前按下的键; 仅运行侧 include (测试目标不链接 raylib)。
- Lua 绑定 `script/api_registry` 的 `register_input(lua_State*, input::Manager&)`: `api.input.bind(action, key, force?)` / `unbind(action)` / `query(action)` / `actions(key)` / `state(action)` / `key(name)`; 键名用字符串, 与配置一致。
- **设计动机**: 与 `log/`、`camera/` 一致, `input/` 纯逻辑核心不依赖 raylib/sol2 (可无头测试), raylib 采样隔离在适配层; 上层 (ECS 移动 system、后续 UI) 只面向「动作」而非具体按键, 为 P1-03 移动 system 提供方向输入。

### 6.12 `world/` — 世界与地图

- `namespace world` — chunk 分块 tile 地图数据层, 纯逻辑核心, 只依赖标准库 + `config::Document`(pimpl 纯头), **不依赖 raylib / sol2 / ecs / event** (可无头测试, 对齐 ADR-9):
  - 坐标约定: 水平面 `(x, y)`(东 = `+x`、南 = `+y`), 层级 `z`(整数, 0 = 地面, 正 = 上层, 负 = 地下室); 高度经 `ecs::Position.z` 表达 (移动模块负责)。tile 坐标为整数 `(x, y)`。
  - `struct TileCoord / ChunkCoord` + 坐标换算纯函数: `world_to_tile`(floor 取整, 负数向下取整) / `tile_to_world`(中心) / `tile_to_chunk` / `chunk_to_tile` / `tile_key`(组合键编解码, x 高 32 位 y 低 32 位)。
  - `enum class Side { North, East, South, West }`(格边方向, n/e/s/w 字符串互转 `side_from_string`/`side_to_string`)、`enum class Stairs { None, Up, Down }`(预留, 楼梯后续需求)。
  - `struct TileDef` — tile 定义: `id`(数值) / `name` / `walkable` / `height`(相对本层基准, 逻辑单位) / `r,g,b`(渲染色) / `texture`(纹理标识, P1 定形不加载)。
  - `struct Level` — 单层: `id` / `width`(x, 可选) / `depth`(y, 可选) / `tiles`(稀疏 tile 映射 `(x,y) 组合键 → 数值 id`, 仅非空) / `interior_tiles`(建筑内标志集合, 见下) / `walls`(边墙列表) / `wall_set`(哈希集查询加速)。
  - `struct Wall` — 边墙 `{cell, side}`, 每面墙唯一表示 (不做双向冗余)。
  - `class World` — 地图容器: `static load(const config::Document&)`(失败 nullopt)、`tile_def(id)`、`level(index/id)`、`is_walkable(level, tile)`、`has_wall(level, tile, side)`(对称查询)、`tile_def_at`、`is_interior(level, tile)`(建筑内, 数据驱动)、`level_height`(层高, 逻辑单位)、`vertical_scale`(垂直缩放)、`level_zs`(所有层级升序)、`tile_size/chunk_size/width/depth`。
- **空 tile（void）语义**: 未声明内容的格子 = 空, `is_walkable=false`、`tile_def_at=nullptr`、不渲染、无碰撞。空与越界统一返回安全默认值。
- **建筑内（interior）语义**: `tiles` 条目可选 `"interior": true`(默认 false), 表示该格为建筑内部空间, 加载时解析进 `Level::interior_tiles`, `is_interior` 查询 (层级不存在/未声明/越界 → false)。纯渲染遮挡语义, 与 walkable / 碰撞无关; 「角色是否在屋内」由 visibility 模块据此数据驱动判定 (取代旧 `has_content_above` 推断, 该接口已移除)。
- **垂直缩放（vertical_scale）语义**: 顶层可选 `"vertical_scale"`(默认 1.0, 必须 > 0, 非法则 load 失败), z 轴 1 个层级单位 = 渲染 `vertical_scale` 个单位 (demo 取 3.0, 即每层 3m)。仅作用于渲染侧 (层基准/墙高/tile 高/玩家 y), 移动与碰撞逻辑 (`pos.z = z × level_height + tile.height`) 不变。
- **掉落逻辑（完整语义, MVP 简化）**: 理论上最底层总有地面 tile, 玩家移动到无 tile 处触发「掉落」直至抵达底层地面 tile 之上; 当前 MVP **简化**为空 tile 直接不可走, 完整掉落/多层高度移动留后续需求。
- **越界安全**: level 越界 / tile 越界 / 未知 tile id / 空 tile 一律返回安全默认值, 不崩溃不抛异常; JSON 缺失字段 / 未知 tile id / 重复 tile id / 重复 tile 坐标 → `load` 失败经 `app_log::error` 报错返回 nullopt。
- **边墙对称查询**: `has_wall(tile, side)` 命中本格该侧或相邻格对侧, 使 P1-03 碰撞从任一格任一边查询结果一致, 无需关心 JSON 把墙写在哪个格。
- **地图 JSON schema** (`config/demo_world.json`): `tile_size` / `chunk_size` / `level_height` / `vertical_scale` / `tile_defs`(对象数组, 数值 id) / `levels[]`(每层 `z/id/width/depth/tiles/walls`)。`tiles` 为**稀疏对象数组** `[{x,y,id,interior?}]`, 未列出 = 空; 只有房屋等结构有内容 (房屋地面格带 `interior` 标志)。
- **设计动机**: 与 `log/`、`config/` 一致, `world/` 是移动/碰撞/渲染共同依赖的地图数据底座, 纯逻辑核心可无头测试; 为 P1-03 移动碰撞提供 walkability/边墙查询, 为渲染遮挡 (visibility/) 提供 interior 与 vertical_scale 数据源。

### 6.13 `movement/` — 移动与碰撞

- `namespace movement` — 纯逻辑移动与碰撞核心, 只依赖 `ecs/components.h` + `world/` + 标准库, **不依赖 raylib / sol2 / input** (可无头单测, 对齐 ADR-9):
  - 依赖 `ecs::Position`(x/y 水平 + z 高度) / `ecs::Mover`(speed + z 层级)（正式组件, 见 §6.9 `components.h`）。
  - `struct MoveResult { bool moved; }` — 移动结果。
  - `MoveResult step(const world::World&, ecs::Position&, ecs::Mover&, float dx, float dy, float dt)` — 沿水平方向 `(dx, dy)`（内部归一化）尝试移动, 纯函数。
- **碰撞算法（轴分离）**: 先 X 后 Y 分轴判定, 贴墙可滑动; 每轴检查 ① 目标 tile `is_walkable` ② **跨格时**（target != from）检查边墙 `has_wall`（按移动方向查对应 `Side`）; 通过才更新该轴坐标。边墙只挡跨线移动, 墙两侧一圈 tile 可正常进入、贴墙移动与站立。
- **高度贴地**: 移动后按 `z × level_height + TileDef::height` 更新 `pos.z`（层级基准高度 + tile 高度）。
- **门洞通行**: 门洞 = 墙排中的缺口（无墙段）, 与普通空地一样可通行; 墙只阻挡跨线移动, 墙两侧 tile 均可进入站立。
- **设计动机**: `movement/` 是 P1-03 的可单测核心, 与 `input/` 解耦（方向向量由场景侧从 `input::action_to_dir` 合成后传入）; 依赖方向 `scene → movement → world/ecs`, `movement/` 不反向依赖 `input/` 或 raylib, 便于后续 Lua 规则复用与无头回归。

### 6.14 `visibility/` — 渲染遮挡判定

- `namespace visibility` — 纯逻辑渲染遮挡判定, 只依赖 `world/` + 标准库, **不依赖 raylib / sol2 / ecs** (可无头单测, 对齐 ADR-9):
  - `struct View` — 玩家视角: 水平世界坐标 `(x, y)` + 所在层 `z`。
  - 每格墙裁剪位: `kCutSouth/kCutEast/kCutNorth/kCutWest`（`uint8_t` 位标志, 沿用 per-cell 结构）。
  - `class Culler` — 遮挡判定器: `update(world, view)` 每固定 tick 重算; `upper_dissolved()`（规则 A）; `is_wall_hidden(wall)`（规则 B）。
- **规则 A 高层内容溶解**（层级 > 玩家层, 整层不渲染）: ① 屋内 (`world.is_interior`)；② 玩家在建筑西北方（玩家层存在 `interior` tile 位于玩家东南象限, 即建筑处于相机前侧）→ 溶解所有更高层, 不做距离判定；玩家在建筑东南方（建筑在屏幕后方）→ 不溶解。
- **规则 B 同层墙透明**（层级 == 玩家层）: 屋内 → 沿玩家行/列（含相邻行列, 覆盖 1 格门洞）找最近南墙线/东墙线, 线上全部南/东墙整排半透明, 北/西墙保留（南/东墙位于相机前侧, 北/西墙在屏幕后方）; 玩家在建筑西北方 → 当前层**所有墙**透明; 玩家在建筑东南方 → 不进行任何透明操作（代码注释预留后续 LOS/窗户检测扩展）。低于玩家层的墙永不隐藏。
- **设计动机**: 遮挡判定是「房屋不能遮挡玩家视线、且尽可能多显示墙与建筑」这一游戏规则的可单测核心; 与渲染解耦（`world_scene` 只消费判定结果）, 「屋内」由地图数据（`interior` 标志）驱动而非运行时推断; 方向二元判定（建筑在玩家东南/西北）简单可预期, 后续引入建筑 ID 与 LOS 时在 no-op 分支扩展, 判定接口不变。

## 7. 关键架构决策

| 编号 | 决策 | 原因 |
|---|---|---|
| ADR-1 | raylib 不通过 vcpkg 获取, 改用 `FetchContent` 源码构建并复用其自带 GLFW | vcpkg 的 raylib 使用外部 glfw3 (`USE_EXTERNAL_GLFW=ON`), 在本项目环境下出现首帧后 swap 忙等、窗口无响应的问题 |
| ADR-2 | ImGui / rlImGui 同样走 `FetchContent`, 固定配套版本 (raylib 6.0 + ImGui 1.92.7 + `Raylib_6_0` tag) | 三者无官方 CMake 集成, 自行构建静态库可精确控制版本配套关系 |
| ADR-3 | Windows triplet 使用 `x64-windows-static-md` 并仅支持 MSVC | vcpkg 在 `project()` 内决定 triplet, 无法自动匹配 MinGW; 预设 triplet 为 MSVC ABI |
| ADR-4 | 所有第三方依赖版本固定 (URL + SHA256 / builtin-baseline) | 保证构建可复现, 避免漂移 |
| ADR-5 | 第三方库按目录封装 (`log/`, `script/`, `model/`) | 隔离头文件冲突, 应用层不直接依赖第三方头文件 |
| ADR-6 | 资源路径用 `resolveAssetPath()` 多级回退解析, 不硬编码工作目录 | IDE 与命令行启动的工作目录不同, 相对路径直接使用不可靠 |
| ADR-7 | 脚本引擎由 PUC Lua (5.4) 切换为官方 LuaJIT (Lua 5.1 + JIT) | 为游戏脚本的高频逻辑 / 热更新提供 JIT 加速与 FFI; LuaJIT API 兼容 Lua 5.1 |
| ADR-8 | C++ 绑定采用 sol2 (header-only), 封装在 `script/lua_engine` | 最主流、生态最大的 C++ Lua 绑定库, 对 LuaJIT 一等支持; 按 ADR-5 隔离 sol2 头文件, 应用层不直接依赖 |
| ADR-9 | 单元测试采用 Catch2, 通过独立测试目标 `project_phoenix_tests` 无头运行 | 纯逻辑层可自动回归; 测试目标不链接 raylib/model_loader (需 GL 上下文与资产), 保证命令行 / CI 可直接运行 |
| ADR-10 | 应用框架采用「App + Game + 固定 tick」结构, 拆分 `main.cpp` | 分离框架外壳与业务载体; 逻辑以固定 30Hz 步长推进、渲染按帧插值, 为后续 ECS / 事件 / 脚本逻辑提供稳定更新基准 |
| ADR-11 | 脚本引擎由一次性求值演进为持久 `sol::state` (`script/lua_engine`), 支持模块加载与基础重载 | 承载跨帧游戏脚本逻辑; 收敛 `lua_runner`(原生 C API 一次性) 与 `sol2_bridge`(自检) 为单一持久引擎, sol2 头经 pimpl 隔离 (ADR-5) |
| ADR-12 | API 绑定框架 (`api.*` 注册约定): 各模块 `register_<module>(lua_State*)` + `register_all` 汇总 | 打通 C++→Lua 调用链, 统一挂 `api.<module>.<func>` 命名空间; 绑定层经裸 `lua_State*` + `sol::state_view`, sol2 头仅出现在 `.cpp` (ADR-5) |
| ADR-13 | 事件总线 (`event/` + `api.event.*`): 同步分发、四类基础类型载荷、`register_event(lua_State*, event::Bus&)` 注入 | C++ 与 Lua 双向解耦通信中介; `event/` 纯 C++ 不依赖 sol2, Lua handler 经 `shared_ptr<sol::protected_function>` 保存防 GC, 载荷经绑定层转换 |
| ADR-14 | 配置系统 (`config/` + nlohmann/json): pimpl 隔离、点分隔路径嵌套访问、路径解析职责分离 | `config/` 纯逻辑不依赖 raylib/asset_path (可无头测试); `load_file` 接受已可用路径, 路径解析由调用方用 `asset_path::resolve` 完成; 解析用非异常 `parse(..., false)` 避免依赖 `/EHsc` |
| ADR-15 | ECS 骨架 (`ecs/` + entt): header-only 薄封装、`Entity = entt::entity`、system 统一更新循环预留 Lua 规则接口 | entt 重度模板化无法 pimpl 隔离, `ecs.h` 作为唯一 include entt 的入口 (精神延续 ADR-5); `Entity` 用 uint32 为后续 Lua number 互转保留语义; 「Lua 规则」= 派发到 Lua 的 `System`(程度一, 仅定形不接 Lua) |
| ADR-16 | 相机系统骨架 (`camera/`): 纯逻辑核心 + raylib 适配层隔离、名称+id 双标识、isometric 位置推导 | `camera/` 核心不依赖 raylib (可无头测试, 对齐 ADR-9), raylib `Camera3D` 转换经独立 header-only 适配层; 相机以名称与 id 双标识方便 Lua 调用; isometric 作为 P0 最小验证载体, 完整跟随/平滑/操控放 P1 |
| ADR-17 | 场景目录组织 (`scene/` 按大类分目录 + `scene::` 子命名空间) + 场景切换载体 (`app::SceneHost`) + 统一顶部场景选择器: 场景按 menu / debug / main_game 等大类分目录, 每类可含多个场景, SceneHost 以「大类/场景名」两级命名在任意场景间自由切换, 渲染帧内绘制统一顶部选择器 | 场景是业务内容, 不应堆在框架层 `app/`; 按大类分目录 + 子命名空间便于组织与扩展, SceneHost 承载切换与懒初始化, 统一顶部选择器要求渲染帧所有权上移到 SceneHost (`Game` 拆分 `render`/`renderUi`), 实现「大类内多场景 + 跨大类自由切换」 |
| ADR-18 | 输入抽象 (`input/` + `api.input.*`): 纯逻辑核心 + raylib 适配层隔离、`enum class Key` + 字符串键名双向转换、命名上下文 + `set_context` 场景切换、静态/动态两层冲突检测 | `input/` 核心不依赖 raylib/sol2 (可无头测试, 对齐 ADR-9); 键名用字符串与 config/Lua 一致; 冲突检测分「静态同上下文同键多动作 (bind 拒绝 + force 覆盖)」与「动态上下文路由 (不同场景/窗口隔离)」两层, P1 落地场景级切换、窗口优先级栈预留 |
| ADR-19 | 世界与地图 (`world/`): chunk 分块 tile 地图纯逻辑核心、数值 tile id + `tile_defs` 对象数组、多层 + 边墙集合、越界安全默认值、边墙对称查询、`config::Document` 数组访问扩展 (`size` + 数字下标段 + `keys` 放宽); 演进为**稀疏 tile 存储** (`tiles` 对象数组 `{x,y,id,interior?}` + 空 tile 语义 + 层 `level_height`) 并新增**建筑内标志** (`interior` + `is_interior`) 与**垂直缩放** (`vertical_scale`, z 1 单位 = 渲染 N 米) | `world/` 是移动/碰撞/渲染共同依赖的地图底座, 纯逻辑核心可无头测试 (对齐 ADR-9); 边墙 `{cell, side}` 唯一表示、`has_wall` 对称查询避免 owner 约定歧义; 越界/非法 JSON 一律安全失败不崩溃; config 数组访问为通用能力 (P1-01 已先例扩展 `keys`); 稀疏 + 空 tile 使「只有房屋有内容」的稀疏地图可高效存储; `interior` 使「角色在屋内/屋外」由数据驱动判定, `vertical_scale` 使层高/墙高按现实比例渲染而不改移动逻辑 |
| ADR-20 | 移动与碰撞 (`movement/` + `ecs/components.h`): 正式组件 `Position`/`Mover` 放 `ecs/components.h`(header-only), 移动碰撞纯函数 `movement::step` 独立成模块, 轴分离碰撞 (X/Z 分轴) + 高度贴地 + 楼梯层级切换 | `movement/` 纯逻辑只依赖 `world` + `ecs/components.h`, 不依赖 raylib/input/sol2 (可无头单测, 对齐 ADR-9); 组件放 `ecs` 供 P1-04 相机跟随 / P1-05 api.ecs 复用, 避免反向依赖 `movement/`; 轴分离实现贴墙滑动、斜向不卡角 |
| ADR-21 | 渲染遮挡 (`visibility/` + `world_scene`): 遮挡判定独立纯逻辑模块, 「屋内」由地图 `interior` 标志数据驱动, 屋外按玩家与建筑的相对方向二元判定 (建筑在玩家东南/相机前侧 → 高层整层溶解 + 当前层全部墙透明; 建筑在玩家西北/屏幕后方 → 不进行任何操作, 预留后续 LOS/窗户扩展); 渲染侧按 `upper_dissolved`/`is_wall_hidden` 消费, **墙面为 2D 平面** (双面四边形 RL_QUADS, 位于 tile 接缝处), 垂直尺寸乘 `vertical_scale` (墙高 3m、上层 3~6m); 地面 tile 2D 平面、网格描边、自由相机、主相机调试保留 | 遮挡规则「房屋不能遮挡玩家视线, 且不遮挡前提下尽可能多显示墙」为纯逻辑可单测; 与渲染解耦, 每格裁剪位结构预留建筑归属等后续扩展; 方向二元判定简单可预期; 墙面 2D 平面贴合「墙 = 接缝线段」的碰撞语义 (raylib 延迟批处理 + 默认背面剔除, 故用双面几何而非运行时切剔除状态); `vertical_scale` 使房屋按现实 3m 层高比例渲染而不改移动/碰撞逻辑 |

## 8. 已知问题与限制

- 尚无 CI 流程 (单元测试已接入 Catch2, 需本地 `ctest` 运行)
- Windows 不支持 MinGW 工具链
- 模型加载为同步阻塞 (`LoadModel`), 26MB 的 GLB 加载约 2~3 秒; 换模型时 UI 会卡顿, 后续需异步加载
- 包围盒绘制仅应用平移不应用旋转; 相机「适配模型」基于未变换的本地包围盒

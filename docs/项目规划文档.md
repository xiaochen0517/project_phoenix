# 项目规划文档

> 版本: v0.1 (2026-10-01)
>
> 本文档记录「僵毁（Project Zomboid）类生存游戏」的整体规划：核心架构原则、模块划分、模拟模型、相机系统、C++/Lua/配置边界、配置化策略与分阶段路线图。
> 它是后续逐模块实现与验证的依据。依赖库、构建、现有模块的技术细节见《项目架构文档》；本文档聚焦「规划」而非「现状」。

---

## 1. 项目定位与目标

- 目标：制作一款类《Project Zomboid》的生存游戏（等距/多视角，僵尸生存、属性/技能、物品合成、NPC/AI、事件）。
- 技术形态：**C++ 核心 + Lua 逻辑 + JSON/XML 配置** 三层架构。
  - C++：定义数据结构（schema）、暴露 API 与高性能基元，负责每帧热路径与资源所有权。
  - Lua：实现绝大部分逻辑与流程（AI、配方、事件、任务、交互、数值公式、相机切换）。
  - 配置（JSON 为主）：承载可在前期确定的静态数据（物品、技能、职业、地图、NPC 等）。
- 交付节奏：先做「核心可玩闭环」，再逐步扩展；每一步可运行、可验证、不推翻前一步。

## 3. 总体架构原则（三层边界）

核心原则只有一条：

> **C++ 定义「数据结构（schema）」和「高性能基元」，Lua 定义「规则与流程」，配置定义「静态数据」。三者由「事件」粘合：C++ 每帧驱动世界并产生事件 → 事件分发给 Lua → Lua 调用 C++ API 修改世界状态。**

### 3.1 C++ 负责

1. 定义所有数据结构的 schema（item / recipe / skill / stat / profession / trait / moodle / tile / chunk / entity 组件…）。schema 一经定义，同时驱动「配置加载」与「存档序列化」。
2. 高性能基元：碰撞、寻路、渲染、chunk 流式、时间推进、资源生命周期。
3. **所有权**：所有游戏对象（实体、物品实例、chunk）由 C++ 持有；Lua 通过**轻量 handle（整数 ID）**引用，不持有所有权，避免双重所有权/悬垂指针。
4. 每帧热路径：实体遍历、物理、渲染。

### 3.2 Lua 负责

1. 规则与流程：AI 决策/行为树、配方合成条件、事件脚本、任务、对话流程、物品交互逻辑、伤害公式、数值计算。
2. 「带逻辑的配置」：当配置需要条件判断或公式时（如「配方需要 5 级木工」），用 Lua 表 + 函数表达。

### 3.3 配置（JSON）负责

1. 纯静态数据：物品属性、技能曲线、职业、特质、Moodle、平衡数值、loot 表、tile 定义、NPC 基础属性。

### 3.4 边界示例（物品「使用」流程）

```text
配置 JSON（物品定义）:
{
  "id": "bandage",
  "type": "medical",
  "weight": 0.1,
  "use_action": "bandage_use"    // 指向 Lua 函数
}

Lua（使用逻辑）:
function item_actions.bandage_use(entity_id, item_id)
  local hp = api.ecs.get_stat(entity_id, "health")
  api.ecs.set_stat(entity_id, "health", hp + 20)
  api.inventory.remove(entity_id, item_id, 1)
  api.event.emit("moodle_update", entity_id)
end

C++（每帧驱动）:
for each entity with Inventory component:
    if input.used_item(entity, slot):            // C++ 检测到「使用」动作
        event_bus.emit("on_item_used", entity_id, item_id)  // 交给 Lua
```

## 4. 模拟模型（固定 tick）

**结论：采用「固定 tick 逻辑 + 可变帧渲染 + 状态插值」。** 与相机视角无关（第一人称/等距都是渲染侧观察方式，逻辑侧时间推进与之正交）。

### 4.1 关键参数

- 固定步长 `FIXED_DT = 1/30`（可配置常量）。
- 累加器（accumulator）驱动逻辑更新，渲染侧以插值系数 `alpha ∈ [0,1)` 在「上一 tick 状态」与「当前 tick 状态」之间插值。

### 4.2 主循环骨架

```text
while (running):
    t = now()
    while (accumulator >= FIXED_DT):
        sample_input()          // 每个 tick 开头采样一次输入（为确定性留后路）
        update(FIXED_DT)        // 逻辑固定步长推进
        accumulator -= FIXED_DT
    alpha = accumulator / FIXED_DT
    render(alpha)               // 渲染在上一状态与当前状态之间插值
```

### 4.3 选型理由

| 维度 | 固定 tick | 帧率驱动 |
|---|---|---|
| 数值稳定 | 稳定 | 低帧率下碰撞穿透/漂移 |
| 可复现/回放 | 能 | 不能 |
| 调试 | 易（单步、重放） | 难 |
| 未来联机 | 平滑升级到确定性同步 | 需大改 |
| 实现复杂度 | 稍高（累加器 + 插值） | 低 |

> 当前为纯单机，暂不实现确定性/网络，但固定 tick 为将来预留了升级路径。

## 5. 模块划分

按「层」组织。现有 `core/log`、`core/script`、`core/model` 已存在，`core/main.cpp` 为单体，后续拆分。

```text
core/
├── app/        框架层：生命周期、主循环、Scene 管理、更新顺序
├── event/      事件总线（C++↔Lua 桥接核心）
├── config/     配置加载 + schema 校验 + 热重载 + 存档序列化
├── ecs/        实体组件系统（Entity/Component/System + 查询）
├── world/      Chunk 分块地图、流式加载、tile、时间/天气、视野
├── resource/   资产异步加载、缓存、引用计数
├── physics/    碰撞、移动、寻路网格
├── camera/     相机系统（多实例 + Lua 配置 + api.camera.*）
├── render/     场景渲染、动画、光照、遮挡剔除
├── audio/      音频播放与空间衰减
├── input/      输入抽象（键鼠/手柄），动作映射可配置
├── script/     持久 lua_State、API 绑定、事件分发、热重载
├── ui/         ImGui（调试/编辑器） + 游戏内 UI（背包/状态/对话/菜单）
├── log/        日志封装（现有，保留）
└── model/      模型加载与动画（现有，保留）
```

各层职责：

| 层 | 模块 | 职责 |
|---|---|---|
| 框架层 | `app` / `event` / `config` | 程序骨架、事件桥、配置与存档 |
| 数据层 | `ecs` / `world` / `resource` | schema 定义与高性能存储 |
| 系统层 | `physics` / `camera` / `render` / `audio` / `input` | 高性能基元（热路径留在 C++） |
| 脚本桥接层 | `script` | Lua 引擎与 API 绑定 |
| 表现层 | `ui` | 调试 UI + 游戏 UI |

> ECS 的 System 骨架在 C++ 跑（每帧、每实体、cache 友好），但 System 的「行为规则」可由 Lua 提供。例：「饥饿随时间下降」的规则是 Lua 函数，「遍历所有实体并对 hunger 组件更新」的循环是 C++ 跑。

## 6. 相机系统设计

原则：**C++ 提供相机原语和每帧数学（高性能），Lua 决定用哪种、怎么配、何时切换（规则）。**

### 6.1 C++ 侧（`camera/` 模块）

1. 相机对象化，支持**多个实例并存**（等距 + 第一人称并存，随时切换；未来分屏 co-op 复用）。
2. 相机类型原语（可扩展）：`isometric`（等距，最先实现）、`first_person`、`third_person`、`orbital`、`manual_fly`。
3. 每帧更新（跟随、平滑、插值）在 C++ 跑，不进 Lua。
4. 暴露可读写属性：`position / target / fov / distance / pitch / yaw / offset` 等，经 API 注册表供 Lua 读写。

### 6.2 Lua 侧（配置 + 操纵）

```lua
-- 相机配置（可在配置文件或 Lua 中定义）
cameras = {
    default = {
        type     = "isometric",
        distance = 32,
        pitch    = 35,
        fov      = 45,
        follow   = { mode = "player", smoothing = 0.12 }
    },
    inspect = {
        type     = "first_person",
        fov      = 60,
        follow   = { mode = "none" }
    }
}

-- 事件回调中操纵相机（切换/跟随/震屏/剧情运镜）
function events.on_pick_lockpick(entity_id)
    api.camera.switch("inspect")
    api.camera.set_follow(entity_id)
    api.camera.shake(0.5, 3.0)
end
```

`api.camera.*` 面：`get_active / switch / set_param / set_follow / shake / list`。

## 7. 配置化策略

### 7.1 格式分工

- **JSON**：主配置格式，纯数据，直接映射 schema，存档也用它。
- **Lua 表**：含逻辑的配置（配方条件、事件、NPC 行为、相机配置）。
- **XML**：默认不使用，仅在明确需要时引入。

### 7.2 可配置化清单

| 类别 | 内容 | 格式 |
|---|---|---|
| 物品/装备 | 武器、服装、食物、药品、材料、书籍 | JSON |
| 技能/职业/特质 | 技能列表、经验曲线、职业起始属性、正负特质 | JSON |
| 状态 Moodle | 饥饿/口渴/疲劳/恐慌等及阈值 | JSON |
| 配方 | 合成配方、需求条件、产物 | Lua 表 |
| 地图/tile | tile 定义、chunk 布局、建筑、道路、loot 表 | JSON（大文件后期可二进制化） |
| NPC | 基础属性、外貌、装备、行为参数 | JSON + Lua |
| 世界生成 | 生物群落、分布、loot 规则、僵尸密度 | JSON / Lua |
| 平衡数值 | 衰减速率、伤害公式参数、经验系数 | JSON（公式本身放 Lua） |
| 事件/任务/对话 | 随机事件、任务链、NPC 对话 | Lua |
| 相机 | 相机类型/参数/切换 | Lua / JSON |
| UI 布局/输入映射 | 键位、UI 元素 | JSON |

## 8. 分阶段路线图

每阶段可运行、可验证，后一步不推翻前一步。

| 阶段 | 目标 | 交付物 | 验证方式 |
|---|---|---|---|
| **P0 骨架** | 三层边界跑通 | 固定 tick 累加器 + 持久 lua_State + API 注册表（含 `api.camera.*`）+ 事件总线 + ECS 骨架 + `app/` 主循环拆分 + JSON schema 加载 | Lua 能读配置、调 API、收发事件 |
| **P1 世界与移动** | 能走的地图 | 等距相机 `isometric` 落地（Lua 配置加载）、chunk 地图、tile、角色移动、碰撞、相机跟随 | 角色在地图上移动、相机正确跟随 |
| **P2 角色系统** | 会饿 | 属性/技能/Moodle、时间系统（固定 tick 驱动）、属性随时间衰减（Lua 规则） | 属性随时间变化、状态正确显示 |
| **P3 物品与背包** | 能捡能用 | 物品 schema、背包、拾取/丢弃/使用（走事件→Lua 边界） | 拾取物品、使用绷带回血 |
| **P4 合成与配方** | Lua 驱动合成 | 配方 schema + Lua 合成逻辑 + 合成 UI | 满足材料时合成成功 |
| **P5 AI 与 NPC** | 会追你的僵尸 | 行为树（Lua）+ 感知 + 寻路 | 僵尸发现玩家并追击 |
| **P6 系统补全** | 可玩闭环 | 战斗、车辆、随机事件、存档/读档 | 完整一局可玩 |
| **P7 打磨与 Mod** | 可扩展 | 热重载、Mod 加载机制、性能优化 | Mod 可加载生效 |

### 8.1 P0 必须现在定死的两项（避免后期返工）

1. 固定 tick：`FIXED_DT = 1/30`，累加器 + 渲染插值。
2. 相机：多实例 + Lua 配置 + `api.camera.*` 可操纵，`isometric` 为第一个相机类型。

## 9. 关键决策记录

| 编号 | 决策 | 原因 |
|---|---|---|
| 规划-1 | 三层边界：C++ schema+基元 / Lua 规则 / 配置数据 | 满足「C++ 暴露规范与 API、Lua 写逻辑、配置承载数据」的目标 |
| 规划-2 | 固定 tick + 插值 | 数值稳定、可回放、为联机预留，且与相机视角正交 |
| 规划-3 | Lua 通过 handle（整数 ID）引用 C++ 对象，所有权归 C++ | 避免双重所有权/悬垂指针 |
| 规划-4 | 相机多实例 + Lua 配置 + `api.camera.*` | 相机是「规则」而非「基元」的一部分，需可配置与可操纵 |
| 规划-5 | JSON 为主配置/存档，Lua 承载含逻辑配置，XML 默认不用 | 数据与逻辑分离，降低复杂度 |
| 规划-6 | 纯单机起步，架构预留事件驱动接口 | 降低初期复杂度，为未来确定性模拟/联机留后路 |
| 规划-7 | MVP 范围 = 核心闭环（移动+属性+物品+合成+追击僵尸） | 快速形成可玩闭环，验证三层边界 |
| 规划-8 | LuaJIT + sol2 | 大量逻辑在 Lua，LuaJIT 执行性能更好；sol2 大幅减少绑定样板代码 |
| 规划-9 | entt + nlohmann/json | 成熟 header-only 库，降低自研成本，聚焦业务 |
| 规划-10 | 测试双轨：Catch2 单元测试 + 表现层手动验证 | P0 骨架多为纯逻辑可自动回归，表现层保留手动验证 |

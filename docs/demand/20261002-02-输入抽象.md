## 需求背景

P0 已落地固定 tick 主循环、事件总线、`config/` JSON 配置、`api.*` 绑定框架、ECS 与相机骨架。P1 总目标「能走的地图」要求角色用 W/A/S/D 在 tile 地图上移动，其第一步是**输入抽象**：把 raylib 的键盘采样封装为「动作」层，隔离输入 API，让上层（ECS 移动 system、后续 UI）只面向「动作」而非「具体按键」。

当前缺失这一层：所有键盘读取若直接调用 raylib（`IsKeyDown(KEY_W)` 之类）会散落在业务代码里，既无法单测（raylib 依赖 GL 上下文），也无法让 Lua 修改键位、无法承载「同一按键在不同场景/窗口触发不同动作」的需求。因此落地最小 `input/` 模块。

## 需求目标

1. 落地最小 `input/` 模块：**纯逻辑核心与 raylib 读取分离**（对齐 ADR-5 / ADR-9），核心可无头单测，raylib 采样在运行侧适配层。
2. 动作表：P1 只做 4 向移动 `move_up / move_down / move_left / move_right`，动作表结构预留扩展（8 向斜移、交互等）。
3. **默认绑定配置**：`config/` 下提供默认绑定 JSON 文件，启动时加载，缺省 W/A/S/D。
4. **暴露 `api.input.*`**：Lua 可读/改绑定（`bind / unbind / query / actions`），遵循 `register_<module>(lua_State*, Manager&)` 注入约定。
5. **按键冲突检测**：静态（同上下文内同键多动作）与动态（跨场景/窗口上下文路由）两层，见 §5。
6. 采样状态机：每固定 tick 开头采样一次，输出「本 tick 动作状态」（Idle / Pressed / Held / Released）。
7. `action_to_dir(action)` 纯函数：按 roadmap §1.1 返回 x/z 单位向量（可单测）。

## 设计方案

### 1. 总体分层

```text
input/
├── input.h        // 纯逻辑核心 (Key / ActionState / BindingMap / Manager / action_to_dir), 无 raylib
├── input.cpp      // 纯逻辑实现 (绑定表、冲突检测、采样状态机、key 名称转换)
└── input_raylib.h // header-only raylib 适配层 (Key ↔ raylib KeyboardKey, 采样读取), 仅运行侧 include
```

- `namespace input`，纯逻辑核心只依赖标准库，不依赖 raylib / sol2 / config（依赖方向 `config → input` 或平级，见 §4 说明）。
- raylib 适配层 `input_raylib.h` 只被运行侧（`scene/main_game` 等）include，测试目标不链接 raylib（ADR-9）。

### 2. Key 枚举与名称映射

为同时满足「纯逻辑可单测」与「config/Lua 可读」，用**自定义 `enum class Key`** + **字符串名称双向转换**：

```cpp
enum class Key {
    Unknown,
    // 字母/数字
    A, B, C, /* ... */ W, X, Y, Z,
    D0, D1, /* ... */ D9,
    // 方向/功能/修饰 (P1 用到的子集, 预留常用键)
    Space, Enter, Escape, Tab, Backspace,
    LeftShift, RightShift, LeftCtrl, RightCtrl, LeftAlt, RightAlt,
    Up, Down, Left, Right,
    F1, /* ... */ F12,
};

// 纯函数 (可单测)
Key key_from_name(const std::string& name);   // "W" → Key::W, "SPACE" → Key::Space, 未知 → Key::Unknown
std::string key_name(Key key);                // Key::W → "W"
```

- 名称规范：单字母用大写 `"W"`，数字用 `"0".."9"`，特殊键用全大写 `"SPACE"` / `"LEFT_SHIFT"` / `"UP"` 等（与 raylib `KeyboardKey` 枚举名对齐、去 `KEY_` 前缀）。
- raylib 适配层做 `Key ↔ raylib KeyboardKey` 双向映射（字母/数字直接复用 ASCII 码，特殊键查表）。P1 仅需 W/A/S/D + 若干常用键，映射表预留扩展。

### 3. 动作表与绑定表 `BindingMap`（含静态冲突检测）

```cpp
// 动作状态 (每 tick 采样一次)
enum class ActionState { Idle, Pressed, Held, Released };

// 绑定结果
enum class BindResult { Ok, Conflict };

class BindingMap {
public:
    // 绑定 action → key; 若 key 已被同表其他 action 占用且未 force, 返回 Conflict 并保留原绑定。
    BindResult bind(const std::string& action, Key key, bool force = false);
    bool unbind(const std::string& action);              // 解绑, 返回是否确实存在该 action
    std::optional<Key> query(const std::string& action) const;   // 动作 → 按键
    std::vector<std::string> actions_for(Key key) const;         // 按键 → 动作列表 (冲突检测/反向查询)
    std::vector<std::string> actions() const;                    // 全部动作名
private:
    std::unordered_map<std::string, Key> action_to_key_;         // action → key
    std::unordered_map<Key, std::vector<std::string>> key_to_actions_; // 反向索引 (冲突检测用)
};
```

- **静态冲突检测**：`bind` 时查 `key_to_actions_`，若该 key 已绑到**本表内**其他 action → 冲突。默认 `force=false` 返回 `Conflict`、保留原绑定并 `app_log::warn` 报告；`force=true` 则顶替原 action（原 action 变为未绑定）。

### 4. Context（上下文）机制 —— 「同一按键触发不同事件」的载体

核心数据结构：`input::Manager` 持有「命名上下文 → BindingMap」的集合，每个上下文有自己的绑定表与优先级：

```cpp
class Manager {
public:
    // 创建/获取命名上下文 (按名幂等), 返回引用。
    BindingMap& context(const std::string& name);
    bool has_context(const std::string& name) const;

    // 设置当前活动上下文 (P1: 场景切换时调用)。
    void set_context(const std::string& name);
    const std::string& active_context() const;

    // 采样: 输入本 tick 的「按键按下集合」, 输出各动作状态 (见 §6)。
    void sample(const std::vector<Key>& pressed_keys);

    // 查询动作当前状态 / 绑定。
    ActionState state(const std::string& action) const;
    std::optional<Key> query(const std::string& action) const; // 活动上下文内查询
    // ...
};
```

- **不同场景**：每个场景一个 Context（命名 = 场景名，如 `main_game` / `debug/model_viewer`），场景切换时 `set_context(name)` 整体切换绑定集。场景 A 的 `W=前进` 与场景 B 的 `W=上移菜单` 互不干扰。
- **同场景不同窗口**：窗口/输入焦点 = 更高优先级上下文（如聊天输入框、模态菜单），临时遮蔽世界移动上下文。P1 采用「**活动上下文 + 优先级栈**」定形（数据上预留 `priority` 与栈接口），采样时从高优先级向低优先级路由，第一个消费该键的上下文生效。
- **P1-01 落地边界**：实现「命名上下文 + 单活动上下文 `set_context`」；「窗口优先级栈」仅预留接口与裁决规则说明，P1 无聊天框/模态窗口，P1-06 之后 UI 需求再实装（见 §5）。

### 5. 按键冲突检测设计（重点）

分两层，分别对应用户提到的两种场景：

#### 5.1 第一层：静态绑定冲突（同一上下文内）

- **问题**：同一 Context 内，一个物理键被绑到多个动作（如误把 `W` 同时绑给 `move_up` 和 `move_down`）。
- **检测时机**：`BindingMap::bind` 调用时，查反向索引 `key_to_actions_`。
- **裁决规则**（P1 定死）：
  1. 默认 `force=false` → 返回 `Conflict`，**拒绝并保留原绑定**，`app_log::warn` 输出「key X 已被 action Y 占用」。
  2. `force=true` → 顶替原 action（原 action 变为未绑定），返回 `Ok`。
- **动机**：绑定是「规则」，规则冲突应显式暴露而非静默覆盖，便于 Lua 脚本/配置文件尽早发现错误；强制覆盖用于「重绑」场景。

#### 5.2 第二层：动态上下文路由（不同场景 / 同场景不同窗口）

- **本质**：这不是「冲突」而是「隔离」——同一 key 在**不同上下文**有不同语义，是设计目标而非错误，因此**跨上下文允许同键不同动作，不触发冲突**。
- **场景级隔离**：不同场景持有独立 `BindingMap`，`set_context` 切换；采样只读当前上下文，天然隔离。
- **窗口级隔离（预留）**：同场景内用「优先级栈」——高优先级上下文（聊天框）先于低优先级（世界移动）匹配按键；匹配到即消费，低优先级不再响应。这实现了「聊天框打开时 W 输入字符而非移动」。
- **统一采样裁决规则**：
  1. 按键状态按上下文优先级（栈顶优先）路由到**唯一**动作。
  2. 高优先级上下文已绑定的键，遮蔽低优先级同键绑定。
  3. 同上下文内不允许同键多动作（由 5.1 静态检测保证）。

> 后续 UI 需求落地「窗口上下文栈」时，`Manager` 增加 `push_context(name, priority)` / `pop_context()`，采样按栈序路由，`BindingMap` 与静态冲突检测逻辑不变（复用 5.1）。

### 6. 采样状态机

`Manager::sample(pressed_keys)` 每固定 tick 开头调用一次（raylib 适配层把「本 tick 按下的所有键」转成 `std::vector<Key>` 传入），内部按上下文路由后对每个动作维护「上一 tick / 本 tick」两态，输出边沿与持续：

| 上一 tick 按下 | 本 tick 按下 | 动作状态 |
|---|---|---|
| 否 | 否 | `Idle` |
| 否 | 是 | `Pressed`（边沿） |
| 是 | 是 | `Held`（持续） |
| 是 | 否 | `Released`（边沿） |

- 纯逻辑核心只依赖「按下集合」这一输入，便于无头单测；raylib `IsKeyDown` 读取放在适配层（运行侧）。
- P1-03 移动 system 读 `Held` 判定持续移动；`Pressed/Released` 边沿供后续 UI/交互复用。

### 7. 动作 → 方向向量（`action_to_dir`）

```cpp
// 纯函数, 按 roadmap §1.1: 北=-z, 东=+x, W=西北。
std::optional<Vec2> action_to_dir(const std::string& action); // move_up → normalize(-1,-1) 等
struct Vec2 { float x = 0.0f; float z = 0.0f; };
```

- 仅 `move_up/down/left/right` 四个动作有映射，其余返回 `nullopt`。
- 方向符号在实现时与相机实际朝向做一次对齐校验后固化（roadmap §5 风险项）。

### 8. 默认绑定配置（config/）

新增 `config/input_bindings.json`（根目录 `config/`，与 `demo_scene.json` 并列）：

```json
{
  "default_context": "main_game",
  "contexts": {
    "main_game": {
      "move_up": "W",
      "move_down": "S",
      "move_left": "A",
      "move_right": "D"
    }
  }
}
```

- 加载职责对齐 ADR-14：`input/` 核心**不做路径解析**；由调用方（运行侧 `scene/main_game` 的 `init`）用 `asset_path::resolve("config/input_bindings.json")` → `config::load_file` 解析 → 逐条 `Manager::bind`。
- 配置缺省或加载失败时，`Manager` 内置默认 W/A/S/D 兜底（`app_log::warn` 提示），保证可运行。
- 为让「config 解析 → 绑定」可单测，提供一个纯函数 `load_bindings(Manager&, const config::Document&)`（或等价接口）：从已解析的 `config::Document` 读 `contexts.<name>.*` 并 `bind`，失败键名经 `app_log::warn` 跳过；此函数只依赖 `config` 与 `input`，可无头测试（`config::Document` 无头可构造/加载）。

### 9. api.input.* 绑定

对齐 `register_event` / `register_camera` 的注入约定，新增 `register_input(lua_State*, input::Manager&)`：

```cpp
// api_registry.h 增补
namespace input { class Manager; }  // 前置声明 (ADR-5)
namespace api {
    void register_input(lua_State* L, input::Manager& manager);
}
```

Lua 接口（键名用字符串，与配置一致）：

| 接口 | 签名 | 说明 |
|---|---|---|
| `api.input.bind` | `bind(action, key, force?)` | 绑定，返回 bool（冲突且未 force 时 false） |
| `api.input.unbind` | `unbind(action)` | 解绑，返回 bool |
| `api.input.query` | `query(action)` | 返回动作绑定的键名 string，未绑定返回 nil |
| `api.input.actions` | `actions(key)` | 返回该键绑定的动作名表（反向查询） |
| `api.input.state` | `state(action)` | 返回动作当前状态（"idle"/"pressed"/"held"/"released"），供调试/脚本 |
| `api.input.key` | `key(name)` | 键名 → key code（辅助，可选） |

- `register_all(Engine&)` 保持不动（只挂无状态 `api.log` / `api.util`）；`register_input` 依赖有状态 `input::Manager`，由调用方（运行侧场景）显式注册，与 `register_event` / `register_camera` 同构。
- sol2 头仅出现在 `api_registry.cpp`，公开头只前置声明 `input::Manager`（ADR-5）。
- `api.input.bind` 内部把 Lua 的字符串键名经 `key_from_name` 转 `Key`，未知键名返回 false 并 `app_log::warn`。

## 确认结果 (2026-10-02)

用户已确认下列决策，按此实现：

1. **键名表示**：config 与 Lua 均用字符串键名（`"W"` / `"SPACE"` / `"LEFT_SHIFT"`），C++ 核心用 `enum class Key` + 双向转换。
2. **静态冲突策略**：同上下文内同键多动作 → 默认拒绝（`Conflict`）+ `app_log::warn`，`force=true` 强制覆盖。
3. **Context 落地边界**：P1-01 实现「命名上下文 + `set_context` 场景切换」；「窗口优先级栈」仅预留接口与裁决规则，UI 需求再实装。
4. **config 文件**：`config/input_bindings.json`，结构 `{ default_context, contexts{ <场景名>: { <action>: "<键名>" } } }`，缺省 W/A/S/D 兜底。
5. **api.input 最小面**：`bind / unbind / query / actions / state`（`key` 可选）。
6. **动作表范围**：P1 仅 `move_up/down/left/right` 四向，斜向/交互动作预留扩展。

> 实现偏差说明：为从 `config/input_bindings.json` 遍历绑定表（`contexts.<名>.<action>`），需给 `config::Document` 增加 `keys(path)` 子键枚举接口（§8 的 `load_bindings` 依赖它）。因此 `input/` 核心对 `config/` 有轻量依赖（`config.h` 为 pimpl 纯头、无第三方类型，不破坏 ADR-5/ADR-9），§1 的「不依赖 config」相应修正为「依赖 config（纯头）」。该 `keys` 接口为通用能力，P1-02 地图 JSON 遍历同样复用。

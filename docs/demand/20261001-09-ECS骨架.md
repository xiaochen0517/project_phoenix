## 需求背景

P0-01 ~ P0-06 已落地依赖与构建、应用框架、Lua 引擎、`api.*` 绑定、事件总线、配置系统。但到当前为止，程序还没有一个**实体组件系统（ECS）**：没有「实体」的概念，也没有「组件挂载 / 查询 / 系统遍历」的骨架，后续的玩家、NPC、游戏对象等业务实体无处承载。

P0 总验收标准要求「各层有单元测试覆盖」，而 P0-09 端到端链路明确包含「ECS 创建玩家实体」这一步。当前缺失 `ecs/` 模块，需要先落地 ECS 骨架，为 P0-09 及后续游戏逻辑打底。

## 需求目标

1. 引入 `entt`（header-only，vcpkg 可用，选型见 roadmap §1），实现 ECS 骨架。
2. 实现 `Registry` 封装：entity 创建 / 销毁 / 存活判定。
3. 实现 component 定义、`attach` / `get` / `has` / `detach`。
4. 实现 `view` 查询与基础遍历。
5. 实现 system 骨架：约定 system 函数签名 + 统一更新循环（供后续 Lua 规则接入）。
6. 单元测试覆盖验收链（创建实体 → 加组件 → view 遍历；销毁实体后组件清理）。

## 设计方案

### 1. 依赖引入

- `vcpkg.json`：新增 `entt`（package 名 `entt`，header-only，版本由 `builtin-baseline` 固定）。
- 顶层 `CMakeLists.txt`：`find_package(EnTT CONFIG REQUIRED)`，提供 target `EnTT::EnTT`（header-only，与 `sol2::sol2` / `nlohmann_json::nlohmann_json` 同构）。
  - > 实现时按 baseline 实际版本核对 target 名与大小写（vcpkg `entt` port 的标准导出为 `EnTT::EnTT`），如有差异在验证结果中记录。

### 2. `ecs/` 模块（纯逻辑，header-only 薄封装）

新增 `core/ecs/ecs.h`（+ 必要的 `core/ecs/ecs.cpp`），`namespace ecs`，只依赖标准库 + entt，**不依赖 raylib / sol2 / lua_engine / config / event**（`ecs/` 是更底层的基础设施，依赖方向为其它模块 → `ecs`，不反向）。

```cpp
// core/ecs/ecs.h
#pragma once

#include <cstdint>
#include <functional>
#include <utility>
#include <vector>

#include <entt/entt.hpp>

namespace ecs {
// Entity: 直接采用 entt 原生实体句柄 (uint32), 为后续 Lua 侧 number 互转保留语义。
using Entity = entt::entity;
inline constexpr Entity null = entt::null;

// Registry: entt::registry 的薄封装, 屏蔽第三方 API 细节, 应用层只接触 ecs:: 类型。
class Registry {
  public:
    // entity 创建 / 销毁 / 存活判定。
    Entity create() { return registry_.create(); }
    void destroy(Entity entity) { registry_.destroy(entity); }
    bool alive(Entity entity) const { return registry_.valid(entity); }

    // component: attach(默认 emplace) / attach_or_replace / detach / has / get。
    template <typename T, typename... Args>
    T& attach(Entity entity, Args&&... args) {
        return registry_.emplace<T>(entity, std::forward<Args>(args)...);
    }

    template <typename T, typename... Args>
    T& attach_or_replace(Entity entity, Args&&... args) {
        return registry_.emplace_or_replace<T>(entity, std::forward<Args>(args)...);
    }

    template <typename T>
    void detach(Entity entity) {
        registry_.remove<T>(entity);
    }

    template <typename T>
    bool has(Entity entity) const {
        return registry_.all_of<T>(entity);
    }

    template <typename T>
    T& get(Entity entity) {
        return registry_.get<T>(entity);
    }

    template <typename T>
    const T& get(Entity entity) const {
        return registry_.get<T>(entity);
    }

    // view: 按组件组合查询, 透传 entt view (range-for 直接迭代 Entity)。
    template <typename... Component>
    auto view() {
        return registry_.view<Component...>();
    }

    template <typename... Component>
    auto view() const {
        return std::as_const(registry_).view<Component...>();
    }

  private:
    entt::registry registry_;
};

// System: 约定统一签名 void(Registry&, float dt)。后续 Lua 规则接入即是一个「内部派发到 Lua」的 System 实现。
using System = std::function<void(Registry&, float)>;

// SystemManager: system 注册 + 统一更新循环。
class SystemManager {
  public:
    // 按注册顺序追加 (P0 不做运行时移除, 移除能力留后续需求)。
    void add(System system);

    // 统一更新循环: 按注册顺序依次调用每个 system。
    void update(Registry& registry, float dt);

  private:
    std::vector<System> systems_;
};
} // namespace ecs
```

要点：

- **header-only 薄封装（ADR-5 的特例处理）**：entt 是 header-only 且重度模板化，`attach<T>` / `get<T>` / `view<T...>` 必须在知道 `T` 完整定义处的调用点实例化模板，无法像 `config` / `lua_engine` 那样用 pimpl 完全隔离第三方头。因此 `ecs.h` 内部 include `<entt/entt.hpp>` 并作为**唯一入口**，应用层只 include `ecs/ecs.h`、不直接碰 `entt::` 类型（精神上延续 ADR-5 的「第三方头经模块封装」）。此点作为确认点 1。
- **Entity = entt::entity**：`entt::entity` 是 `std::uint32_t` 的别名，天然可序列化为 Lua `number`，为 P0-09 之后「Lua 规则接入」保留互转语义；对外统一用 `ecs::Entity` 别名，不暴露 `entt::entity` 原始名（确认点 3）。
- **view 透传**：`view<Component...>()` 返回 entt view，range-for 直接迭代出 `Entity`；`each()` 可迭代 `(Entity, Component&...)` 元组，测试用「view 遍历计数」覆盖验收标准。
- **预留 Lua 规则接口（程度一：仅定形、不接 Lua）**：P0 阶段把「规则」这个扩展点**定死**——`System` 就是稳定的函数签名 `void(Registry&, float)`，`SystemManager` 提供注册 + 按序 `update`，接受任意 system。未来「Lua 规则」= 一个内部派发到 `lua_engine::Engine` 的 `System`（`script/` 侧适配器构造），**无需改动 `ecs/` 即可接入**。依赖方向为 `script/ → ecs/`，本阶段 `ecs/` 不引入任何 Lua 依赖、保持纯 C++、可无头测试（确认结果 2）。

### 3. 目录与文件结构

```
core/ecs/
├── ecs.h             // 新增: Registry (header-only 模板) + System + SystemManager 声明
└── ecs.cpp           // 新增: SystemManager::add / update 实现 (非模板)
```

### 4. 单元测试（`tests/test_ecs.cpp`）

测试不依赖任何资产与路径注入（纯内存逻辑，无 `PROJECT_PHOENIX_*_DIR`）。测试用组件在测试文件内定义：

```cpp
struct Position { float x; float y; };
struct Velocity { float vx; float vy; };
```

| 用例 | 验证点 |
|---|---|
| 创建实体 / 存活判定 | `create()` 返回非 `null`；`alive(e)` 为 `true` |
| 销毁实体 | `destroy(e)` 后 `alive(e)` 为 `false` |
| attach / get / has 组件 | `attach<Position>(e, 1.0f, 2.0f)` 后 `has<Position>(e)` 为 `true`、`get<Position>(e)` 返回同一引用且值正确 |
| attach_or_replace / detach | `attach_or_replace` 覆盖旧值；`detach<Position>(e)` 后 `has` 为 `false` |
| view 遍历得到正确实体数 | 给 3 个实体 attach `Position`、其中 2 个 attach `Velocity`；`view<Position>()` 遍历数为 3，`view<Position, Velocity>()` 遍历数为 2 |
| 销毁实体后组件被正确清理 | attach 组件后 `destroy(e)`，`view<Position>()` 遍历数减少到 0 |
| system 统一更新循环 | 注册多个 lambda system（各自累加计数/修改组件），`update` 按注册顺序全部调用、`dt` 透传正确 |

## 确认结果 (2026-10-01)

1. **entt 头文件隔离（ADR-5 特例）**：接受「header-only 薄封装」——`ecs.h` 内部 include `<entt/entt.hpp>`、作为全项目**唯一** include entt 的地方，应用层只 include `ecs/ecs.h`、只接触 `ecs::` 类型，不直接写 `entt::`；不采用 pimpl（entt 重度模板化，pimpl 隔离收益几乎为零）。精神上延续 ADR-5「应用层不直接依赖第三方头」，实现上不 pimpl。
2. **system 骨架范围**：接受「预留 Lua 规则接口（程度一：仅定形、不接 Lua）」——P0-07 定死 `System` 签名 + `SystemManager` 统一更新循环，明确记录「Lua 规则 = 派发到 `lua_engine` 的 `System`（`script/` 侧适配器构造）」，本阶段 `ecs/` 不引入 Lua 依赖、保持纯 C++、可无头测试。
3. **Entity 类型形态**：接受 `ecs::Entity = entt::entity`（uint32），不另造不透明句柄，为后续 Lua number 互转保留语义。
4. **组件接口命名**：接受 `attach` / `attach_or_replace` / `detach` / `has` / `get` / `view` 这一组命名（emplace / emplace_or_replace / remove / all_of / get / view 的直译封装）。

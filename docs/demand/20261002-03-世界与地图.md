## 需求背景

P1 总目标「能走的地图」需要一个 tile 地图数据层作为移动/碰撞/渲染的共同底座。P0 已落地 `config/`（JSON 加载）、`ecs/`（实体骨架）、`input/`（方向动作）、`camera/`（相机骨架），但尚缺「地图」本身：tile 定义、多层结构、边墙/整格阻塞、chunk 分块与坐标换算。

P1-01 已把「输入方向」与「按键」解耦，P1-02 承接的正是输入的方向向量所作用的那张「能走/不能走」的地图。roadmap 已定案：64×64 地图、chunk 16×16（4×4 chunk）、MVP 2 层（ground + upper）、边墙为主 + 整格阻塞补充、JSON 存储、`world/` 纯逻辑不依赖 raylib/sol2（可无头单测）。

本需求落地最小 `world/` 模块与地图 JSON schema，为 P1-03 移动与碰撞提供 walkability / 边墙 / 楼梯查询，为 P1-06 渲染提供 tile 定义（颜色/高度/纹理标识）。

## 需求目标

1. 落地 `world/` 模块：**纯逻辑核心，不依赖 raylib / sol2 / ecs**（可无头单测），依赖 `config::Document`（纯头，对齐 ADR-14）。
2. **tile 定义表**（`tile_defs`）：`id / name / walkable / height / color / texture / stairs?`，从 JSON 载入；地图格内只存 id。
3. **多层结构**：`levels[]`，每层独立 tile 平面 + 边墙集合；MVP 2 层（ground + upper），数据结构支持任意层。
4. **边墙集合**：每面墙 `{x, z, side}` 唯一表示（不做双向冗余），与整格阻塞 tile 共享 walkability 判定。
5. **chunk 分块**：64×64 按 16×16 切 4×4 chunk，逻辑上分块查询（存储整体一份 JSON，加载后切块）。
6. **坐标换算**：`world→tile`、`tile→chunk`、`tile→world`（tile 中心）等纯函数（可单测，含负数与边界）。
7. **查询接口**：`is_walkable` / `has_wall` / `tile_def` / `stairs`；JSON 加载失败经 `app_log` 报错返回空。
8. 提供示例地图 JSON 资产（运行侧用）+ 测试 JSON 资产（单元测试用）。

## 设计方案

### 1. 总体分层与文件结构

```text
core/world/
├── world.h        // 纯逻辑核心: TileCoord/ChunkCoord/Side/TileDef/Level/World + 坐标换算纯函数
└── world.cpp      // 实现: 从 config::Document 加载、walkability/边墙/楼梯查询
core/tests/
└── test_world.cpp // 单元测试 (坐标换算/加载/查询/非法输入)
config/
└── demo_world.json     // 运行侧示例地图 (64×64, 2 层)
config/test/
└── test_world.json     // 测试用精简地图 (小尺寸, 便于断言)
```

- `namespace world`，只依赖标准库 + `config::Document`（pimpl 纯头），不依赖 raylib / sol2 / ecs / event。
- 路径解析职责分离（ADR-14）：`world/` 核心只接收已解析的 `config::Document`，运行时由调用方用 `asset_path::resolve` 定位文件后 `config::load_file` 再传入；单元测试用 `PROJECT_PHOENIX_CONFIG_DIR` 注入绝对路径。

### 2. 坐标与方向约定（固定）

沿用 roadmap §1.1 的 3D 世界约定：

- 世界坐标 `(x, y, z)`，`y` 为高度（向上），移动发生在 `x/z` 水平面。
- 北 = `-z`，东 = `+x`，南 = `+z`，西 = `-x`。
- tile 坐标为整数 `(x, z)`，`tile_size` 为世界单位/格（默认 1.0）。

纯函数（全部可单测）：

```cpp
struct TileCoord  { std::int32_t x; std::int32_t z; };
struct ChunkCoord { std::int32_t x; std::int32_t z; };

// 世界 → tile: floor 取整 (负数向下取整, 保证 -0.1 → -1)
TileCoord world_to_tile(float wx, float wz, float tile_size);
// tile → 世界 (tile 中心)
void tile_to_world(const TileCoord& t, float tile_size, float& wx, float& wz);
// tile → chunk: floor(tile / chunk_size)
ChunkCoord tile_to_chunk(const TileCoord& t, std::int32_t chunk_size);
// chunk → tile (chunk 原点 tile 坐标)
TileCoord chunk_to_tile(const ChunkCoord& c, std::int32_t chunk_size);
```

> `floor` 语义固定为「向下取整」：负数坐标 `world_to_tile(-0.1)` → `-1`，避免跨格时的坐标跳变（roadmap §5 风险「高速穿透」虽在 P1-03 处理，坐标换算本身要先保证负半轴正确）。

### 3. tile 定义表（`tile_defs`）

`TileDef` 字段集（含纹理标识，本阶段**只定形、不加载纹理**，纹理资产加载属后续 resource/ 范畴）：

```cpp
enum class Stairs { None, Up, Down };

struct TileDef {
    std::int32_t id = 0;   // 数值 id (tile 地图格内引用)
    std::string name;      // 显示名 (UI 用, 可中文)
    bool walkable = true;  // 整格是否可走
    float height = 0.0f;   // tile 的 y 高度 (渲染高度/台阶高度)
    float r = 0.5f, g = 0.5f, b = 0.5f;  // 渲染颜色 (P1 纯色渲染)
    std::string texture;   // 纹理标识/路径 (空 = 无纹理); P1 定形不加载
    Stairs stairs = Stairs::None;        // 楼梯方向 (None=非楼梯)
};
```

- tile 用**数值 id**（`std::int32_t`），地图格内只存 id；`texture` 为字符串标识，空串表示无纹理，P1-06 渲染阶段仍以纯色绘制、`texture` 字段预留。

### 4. 地图 JSON schema（最终）

```json
{
  "name": "demo_world",
  "tile_size": 1.0,
  "chunk_size": 16,
  "tile_defs": [
    { "id": 1, "name": "草地",    "walkable": true,  "height": 0.0, "color": [0.35, 0.60, 0.30], "texture": "" },
    { "id": 2, "name": "石板",    "walkable": true,  "height": 0.0, "color": [0.50, 0.50, 0.50], "texture": "" },
    { "id": 3, "name": "墙体",    "walkable": false, "height": 1.0, "color": [0.45, 0.38, 0.32], "texture": "" },
    { "id": 4, "name": "上行楼梯", "walkable": true,  "height": 0.0, "color": [0.85, 0.65, 0.25], "texture": "", "stairs": "up" },
    { "id": 5, "name": "下行楼梯", "walkable": true,  "height": 0.0, "color": [0.85, 0.65, 0.25], "texture": "", "stairs": "down" }
  ],
  "levels": [
    {
      "id": "ground",
      "width": 64,
      "depth": 64,
      "tiles": [ 1, 2, 1, "..." ],
      "walls": [ { "x": 10, "z": 20, "side": "n" } ]
    },
    {
      "id": "upper",
      "width": 64,
      "depth": 64,
      "tiles": [ "..." ],
      "walls": []
    }
  ]
}
```

要点：

- `tile_defs` 为**对象数组**，每项含数值 `id` + 属性；加载时构建 `id → TileDef` 索引（id 重复 → 加载失败报错）。
- `tiles` 为数值 id 数组，长度 `width × depth`，**x 优先（row-major）**：索引 `i = z * width + x`。
- `walls` 为 `{x, z, side}` 对象数组；`side` 取值 `"n" / "e" / "s" / "w"`，表示格 `(x,z)` 的哪条边有墙。约定：`"n"` = 该格朝向 `-z` 的一侧（北边），`"s"` = `+z`，`"e"` = `+x`，`"w"` = `-x`（全项目统一，roadmap §5 风险项）。
- `color` 为 `[r, g, b]` 三元素数值数组。
- `stairs` 取值 `"up" / "down"`（省略或空 = 非楼梯）。
- Level 用 `width`（x 方向）+ `depth`（z 方向）命名，避免与 `TileDef.height` 的「高度」语义冲突。
- 每层 `width/depth` 独立声明（虽然 MVP 都是 64×64，结构支持任意尺寸）。

### 5. 边墙与 walkability

- 边墙与整格阻塞 tile（`walkable=false`）**共享** `is_walkable` 判定；区别在于边墙只挡「跨过该边」的移动，整格阻塞挡「进入该格」。
- 边墙集合存储为哈希表（`TileCoord + Side` 组合键），**每面墙只存一次**（JSON 里不写双向冗余条目）。
- `has_wall(tile, side)` 采用**对称查询**：返回 true 当且仅当墙集里存在 `{tile, side}` **或** 相邻格 `{neighbor, opposite(side)}`。这样 P1-03 碰撞代码从任一格的任一边查询结果一致，无需关心 JSON 作者把墙写在哪个格上；存储仍保持「一条墙一个条目」。

### 6. 查询接口（`World`）

```cpp
class World {
  public:
    // 从 config::Document 加载地图; 失败返回 nullopt (经 app_log::error)。
    static std::optional<World> load(const config::Document& doc);

    // tile 定义 (按数值 id)
    const TileDef* tile_def(std::int32_t id) const;

    // 层级
    std::int32_t level_count() const;
    const Level* level(std::int32_t index) const;
    const Level* level(const std::string& id) const;

    // 查询 (level 越界/坐标越界一律返回「不可走」安全值, 不崩溃)
    bool is_walkable(std::int32_t level, const TileCoord& t) const;
    bool has_wall(std::int32_t level, const TileCoord& t, Side side) const;
    const TileDef* tile_def_at(std::int32_t level, const TileCoord& t) const;  // 格上 tile 的 def
    Stairs stairs_at(std::int32_t level, const TileCoord& t) const;            // 格上楼梯方向

    // 全局参数
    float tile_size() const;
    std::int32_t chunk_size() const;
    std::int32_t width(std::int32_t level) const;   // x 方向格数
    std::int32_t depth(std::int32_t level) const;   // z 方向格数
};
```

- 越界（level 不存在、tile 超出 `[0,width)×[0,depth)`）统一返回安全默认值：`is_walkable=false`、`has_wall=false`、`tile_def_at=nullptr`、`stairs=None`，不崩溃、不抛异常（对齐 §7 验收「非法/越界查询报错不崩溃」）。
- `stairs_at` 返回 `Stairs` 枚举（含 `None`），供 P1-03 触发层级切换。

### 7. chunk 分块

- 常量 `chunk_size`（16），64×64 地图切 4×4 chunk。存储上每层仍是「一张完整 tile 数组 + 一个墙集」，加载后**逻辑上**按 `tile_to_chunk` 分区，不做物理拷贝（P1 无流式加载需求）。
- 提供 `tile_to_chunk` / `chunk_to_tile` 纯函数；chunk 级空间查询（「某 chunk 内所有 tile」）留待 P1 后续需要流式/分块渲染时再补，P1-02 只落地坐标换算。

### 8. config 扩展（实现偏差说明）

`config::Document` 现有接口（`get_*` 点路径、`keys`、`validate`）只支持对象遍历与叶子读取，**无法读取数组元素**。地图 JSON 的 `tile_defs`（对象数组）、`tiles`（数值 id 数组）、`walls`（对象数组）与 `color`（数值数组）必须支持数组访问，故需对 `config/` 做最小扩展（与 P1-01 增加 `keys()` 同类，属通用能力，P1-03 之后也可能复用）：

1. `keys(path)` 放宽：数组节点也返回索引字符串 `"0".."N-1"`（当前实现仅对象返回，需移除 `!is_object()` 的过早拦截，nothrow 下 nlohmann 对数组迭代 `it.key()` 本身就是索引字符串）。
2. 点路径支持**数字下标段**：`find_node` 遇到全数字段（如 `"levels.0"`、`"tile_defs.0"`、`"tile_defs.0.color.0"`）时对数组按索引取值。这样 `get_int("tile_defs.0.id", -1)` / `get_string("tile_defs.0.name", "")` / `get_double("tile_defs.0.color.1", 0.0)` 可直接复用。
3. 新增 `std::int64_t size(const std::string& path)`：返回数组/对象元素个数，节点不存在或非容器返回 `-1`，供 `world/` 读取 `tile_defs` / `levels` / `tiles` / `walls` 的长度。

> 该扩展仅加能力、不改既有行为；`config/config.cpp` 无第三方新依赖，`test_config.cpp` 补数组访问相关用例。

## 确认结果 (2026-10-02)

用户已确认下列决策，按此实现：

1. **tile_defs 字段集**：现在即加入**纹理字段**（`texture`，字符串标识，空 = 无纹理）；P1 阶段只定形、不加载纹理，渲染用纯色。
2. **tile id 表示**：用**数值 id**（`std::int32_t`）；`tile_defs` 相应为对象数组，加载时构建 `id → TileDef` 索引。
3. **JSON schema 结构**：按文档 §4（`tile_defs` 对象数组 + `levels[]`，每层 `width/depth` + `tiles` 一维数组 x 优先 + `walls` 边墙数组）。
4. **地图规模**：保持 roadmap MVP 值 64×64 / chunk 16×16 / 2 层 / `tile_size=1.0`。
5. **config 扩展**：同意对 `config::Document` 做最小扩展（数组下标段 + `size()` + `keys()` 放宽）。
6. **边墙查询**：`has_wall` 采用对称查询（本格 + 相邻格对侧均命中），避免 owner 约定歧义。

## 需求背景

P0-03 已落地持久 `lua_engine::Engine`（`do_file` / `reload` / `call_function`），Lua 能加载脚本、调用全局函数，但**脚本侧还拿不到任何 C++ 能力**——`call_function` 只能调用 Lua 侧定义的函数，C++ 函数无法被 Lua 反向调用。

P0 总验收标准要求「Lua 能读配置、调用 API、收发事件」，其中「调用 API」依赖一条 **C++→Lua 的调用链**：C++ 把业务函数暴露到 Lua 侧命名空间，Lua 脚本直接 `api.xxx.yyy(...)` 调用。当前缺失这一层，需要建立 `api.*` 注册表结构与统一绑定框架。

## 需求目标

1. 建立 `api.<module>.<func>` 命名空间约定与注册表结构，各业务模块提供自己的 `register_*`，统一挂到 `api` 表下。
2. 打通 C++→Lua 调用链：绑定 `api.log.*` 作为基础验证 API，Lua 能调用并取到 C++ 返回值。
3. sol2 头文件继续隔离在 `.cpp`（ADR-5），应用层 / 公开头文件不暴露 sol2。
4. 单元测试覆盖两条验收链：Lua 调 `api.log.info(...)` 输出日志；Lua 调 API 取到 C++ 返回值。

## 设计方案

### 1. `api.*` 注册约定（命名规范 + 注册入口形式）

- **命名规范**：所有 C++ 暴露给 Lua 的能力统一挂到 `api.<module>.<func>`，例如 `api.log.info`、`api.event.on`（P0-05）、`api.ecs.*`（P0-07）、`api.camera.switch`（P0-08）。在 sol2 中实现为嵌套 `sol::table`：`api` 表下每模块一个子表，函数挂子表字段。
- **注册入口形式**：**每个业务模块提供一个 `register_<module>(lua_State *)` 函数**，签名统一为裸 `lua_State*`（见 §2，sol2 头仅在 `.cpp`，公开声明用 `struct lua_State;` 前置声明）。模块内部用 `sol::state_view(L)` 包装裸指针后做 sol2 绑定。
- **汇总入口**：`api::register_all(lua_State *)` 依次调用所有 `register_*`。新增模块时：在 `api_registry.h` 声明其 `register_*`，在 `register_all` 中追加一行调用即可，`api.*` 注册表结构随之自动扩展。

> 这是 roadmap §5 标记的 P0-04 实现前确认点（「是否每个模块一个 `register()` 函数」）的落地方案，见文末「确认点」。

### 2. `Engine` 暴露原始 state

`api_registry` 绑定需要拿到 `Engine` 内部的 `sol::state`。为遵守 ADR-5（sol2 头不向公开头文件暴露），采用**裸 `lua_State*` 访问器**：

```cpp
// core/script/lua_engine.h 增补
struct lua_State; // 前置声明, 不 include lua.h / sol2

class Engine {
public:
    // 供 api 绑定层使用: 返回内部 sol::state 的裸 lua_State* (sol2 头仅在 .cpp, ADR-5)。
    lua_State *raw_state();
    // ... 既有接口不变
};
```

实现（`lua_engine.cpp`）：`return impl_->lua.lua_state();`（`sol::state` 的 `lua_state()` 返回裸 `lua_State*`）。

绑定层拿到 `lua_State*` 后用 `sol::state_view lua(L)` 包装即可做 sol2 绑定，`sol::state_view` 不接管内存，生命周期仍由 `Engine` 负责。

### 4. 绑定实现（P0-04 范围）

`api_registry.cpp` 核心结构：

```cpp
#include <sol/sol.hpp>
#include "log/app_log.h"
#include "script/api_registry.h"

namespace api {
    namespace {
        void register_log(lua_State *L) {
            sol::state_view lua(L);
            sol::table api = lua["api"].get_or_create<sol::table>();
            sol::table log = api["log"].get_or_create<sol::table>();
            log["debug"]    = &app_log::debug;
            log["info"]     = &app_log::info;
            log["warn"]     = &app_log::warn;
            log["error"]    = &app_log::error;
            log["critical"] = &app_log::critical;
        }
    }

    void register_all(lua_engine::Engine &engine) {
        lua_State *L = engine.raw_state();
        register_log(L);
        // 后续: register_event(L); register_camera(L); register_ecs(L); ...
    }
}
```

要点：

- `api.log.*` 直接绑定 `app_log::*`（`void(const std::string&)`），sol2 自动完成 `std::string` 参数转换，满足「输出日志」验收。
- `get_or_create<sol::table>()` 保证 `api` / `api.log` 表幂等创建，模块间互不覆盖。
- 为满足「取到 C++ 返回值」验收，另绑定一个**最小返回值演示 API** `api.util.add(a, b)`（`double` 相加），用于打通 C++ 返回值回传 Lua 的链路（见「确认点」，可调整命名/位置）。

### 5. 单元测试（`tests/test_api_bindings.cpp`）

| 用例 | 验证点 |
|---|---|
| Lua 调 `api.log.info` 输出日志 | `register_all` 后 `do_file` 加载脚本 `api.log.info("from_lua")` → 捕获 spdlog 输出断言出现 "from_lua" |
| Lua 调 API 取到 C++ 返回值 | 脚本定义 `function api_value() return api.util.add(2, 3) end` → `call_function("api_value")` 返回 `5.0` |
| 未注册模块不可调用 | 直接调用未绑定命名空间（如 `api.event.on`）时脚本报错不崩溃，`do_file` 返回 `false` |

「输出日志」捕获方案：测试内用 `spdlog::sinks::ostream_sink_mt` 新建临时 logger 并 `spdlog::set_default_logger` 替换默认 logger，断言 `std::ostringstream` 内容后恢复原 logger（`app_log::info` 走 `spdlog::info`，会命中默认 logger）。spdlog 已链接测试目标，无需改动 `app_log`。

测试脚本沿用 `lua/` 目录（如 `lua/test_api_log.lua`），路径经 `PROJECT_PHOENIX_LUA_DIR` 拼绝对路径（P0-03 已建立）。

## 确认结果 (2026-10-01)

1. **注册入口形式**：认可「每个模块一个 `register_<module>(lua_State *)` + 汇总 `register_all`」，签名统一为裸 `lua_State*`（sol2 仅在 `.cpp`，公开头只前置声明）。
2. **返回值演示 API**：接受 `api.util.add(a, b)` 作为最小演示，打通 C++ 返回值回传 Lua 链路。
3. **运行时接入范围**：P0-04 仅单元测试验证，`app/` 暂不注册 `api.*`，运行时链路留到 P0-09。
